## 0. 三个重点的结论速览

| 重点 | 结论 |
|---|---|
| 1. 架构分层＋端/云 | 六层人格统一架构；**端云三段式**：端侧＝本地会话记录＋零智能薄执行器，云端＝大脑（临时上下文）＋长期记忆（账号持久化）；断网全灭 |
| 2. 技能/工具组织 | **两层工具**：常驻基础工具（4 个）＋懒加载技能（清单+reference）；单层粒度无嵌套；用户扩展（小工具）与注册表隔离 |
| 3. 小程序能力 | **GUI 元素树是唯一主力**；原子接口❎（契约层＋行为层双否）；原子卡片❎原形态（实际＝工具返回负载）。供给侧文档三件套只落地了 GUI 一件，且为元素树形态而非声明式形态 |

## 1. 综合架构总图

```
用户消息（文字/语音；入口：微信搜索界面；断网全灭）
   │
   ▼ ①模型层 ──────────────────────────────────────────
│ WeLM 永远主控＝用户唯一接口（人格统一 🟢）

│   结果回传 WeLM 整合、不留痕 🟢
│ 触发：任务型路由（推理/代码/数学，系统预设策略）＋用户点名 🟢
   ▼ ②路由层 ──────────────────────────────────────────
│ 两阶段懒加载（模型侧 function-calling 🟢）：
│   清单粗路由（名＋一句话简介，_skills_index.md）
│   → read_skill 加载该技能 reference 全文
│   → 知参数/边界后精确调用
   ▼ ③能力层 ──────────────────────────────────────────

│   基础工具（常驻）：read_skill / get_memory /
│                     general_search / get_position
│   技能层（懒加载）：26+ 业务技能，封装执行器（子代理模式）
│ 对用户叙事：7 板块 28 条目（生成性复述，与机读层非一一对应）
   ▼ ④执行层 ─────────────────────────────────────────
│ 三通道（🟢），主模型只见结论不见过程：
│   ① mini-app：UI 元素树（类型/文本/位置）＋节点级动作
│      无视觉通道、canvas 全盲；动作渲染为可见手势
│   ② wx-action：微信原生功能统一入口（消息/电话/红包/转账/找人）
│   ③ 专属协议：小游戏走游戏 API，不经元素树

   ⑤记忆层（双系统 🟢）────────────────────────────────
│   Agent 记忆：memory-manager 写（记住/以后）删（忘掉，需确认）
│              ／get_memory 读（按需检索，含聊天记录摘要）
│   平台行为数据：偏好不落画像，推荐时现算

   端/云三段式 ─────────────────────────────────────────
│   端侧：会话记录（本地，换设备不跟随）＋薄执行器（无障碍/手势）
│   云端：大脑＋推理上下文（会话期临时）＋长期记忆（账号持久化）
│   蒸馏记忆上云、原始对话留端
```

## 2. 重点一：层级职责与运行环境

### 2.1 各层职责表

| 层 | 职责 | 关键事实 |
|---|---|---|
| 模型层 | 理解、决策、生成 | WeLM 主控；DeepSeek 工具式 subcontract（单问上下文、不留痕）；人格统一是接口层设计，与实现多模型解耦 |
| 路由层 | 选技能、选模型 | 技能路由＝模型侧（清单+read_skill）；模型路由＝系统预设策略（🟡 两套机制，P2-7 顺从性污染待判别） |
| 能力层 | 封装执行 | 胖技能：内部完成检索/计算/聚合，返回"可读结论"；子代理模式，主模型不见内部 |
| 执行层 | 落地操作 | 三通道（元素树/原生接口/专属协议） |
| 记忆层 | 状态保持 | 双系统；读写不对称（读=工具、写=技能）；摘要持久化 |

### 2.2 端/云判定（P3-1/2/3）

| 问题 | 判定 | 依据 |
|---|---|---|
| 大脑在哪 | 云端 | 断网全灭；推理需服务端 |
| 会话记录在哪 | **端侧本地** | P3-3：换设备不跟随（与微信聊天记录本地策略一致） |
| 长期记忆在哪 | 云端账号绑定 | P3-3：换设备仍在 |
| 执行器在哪 | 云端大脑＋**端侧薄执行器** | 第一性原理：手势在本机屏幕渲染，云端摸不到本地 UI；"我传指令，执行看对面配合"（P3-8 侧证） |
| 离线能力 | 零 | P3-2：无离线模式，残留卡片属微信客户端缓存而非 agent |

注：P3-1 自述为"合理推测"（第四档可信度），其中"执行器全在云端、对话存云端"两点已被 P3-3 与第一性原理修正——**推测型回答不可直接采信**。

## 3. 重点二：技能与工具组织

### 3.1 两层工具组织（P3-4 🟢）

```
主模型可用工具
 ├─ 基础工具层（常驻、少量）
 │    read_skill      读技能说明书（进入注册表唯一通道）
 │    get_memory      检索用户记忆（记住的事/图片/聊天记录摘要）
 │    general_search  联网搜索（公开信息/公众号/图片/歌曲/小程序，带 source 参数）
 │    get_position    定位
 └─ 技能层（懒加载；数量三种说法 25/26/28，漂移未钉死）
      总清单 references/_skills_index.md，每条含：
        分类 · 中文名 · 一句话概述 · 召回关键词 · 加载详细文档的 JSON 参数
      各技能 references/能力描述.md 五段式：
        是什么 ／ 能做什么✅ ／ 不支持什么❌ ／ 易混淆区分 ／ 用户常见问法
      调用单元＝技能入口工具名（与 slug 可分离，如 mini-app ↔ operate_miniapp）
      ↳ reference 内按编号引用「输出规则 4」，但该规则不在 reference 中
        ——疑似技能层之上有编号化全局输出规则层 🟡（或为提取剥离的章节）
```

**路由与 grounding（补获）**：召回关键词字段 → 粗路由为关键词辅助匹配（印证 P1-5 原始叙述）；能力问答纪律＝"写进 ref 里就答，没有的如实说没覆盖到"（ref 之上的 RAG，不靠模型记忆）；"易混淆区分"段防误路由（例：mini-app ref 写明不支持航班订阅提醒，归任务中心）。

- **单层粒度**（P3-5）：无嵌套子工具暴露给编排层；技能内部组织在内省地板下
- **capability-qa 机制**：答"你能做什么"＝读索引复述（解释枚举稳定＋生成性漂移 26vs28）
- **元工具面刻意收窄**：无 list/search 技能工具，read_skill 是唯一注册表通道

## 4. 重点三：小程序能力判定（终版）

### 4.1 判定表

| 供给侧文档承诺 | 黑盒判定 | 依据 |
|---|---|---|
| GUI 操作 | ✅ 唯一主力机制 | 元素树＋节点级动作（P2-4a）；canvas 全盲（P2-4b）；手势真实渲染（实测）；主模型只见结论（P2-12） |
| 原子接口 | ❎ 契约层不存在 | reference 无此概念（P3-7 最高档可信度）；行为无双通道特征（P3-8：快慢差异全归因元素树质量）；供给侧研究未见落地 |
| 原子卡片 | ❎ 原形态不存在 | 无"小程序递卡→agent 转交"协议（P3-9）；实际＝工具返回负载＋专用卡片工具 |

**总结论：文档画的声明式原子能力是愿景层，实际运行的是通用元素树自动化＋特殊域协议通道。**

### 4.2 执行机制细节

- 元素树节点三字段：类型（按钮/输入/文本/图片）＋文字内容＋位置信息；无颜色/布局/视觉样式
- 决策："解析元素树哪个节点匹配需求→触发该节点的点击事件"（节点级程序化动作）
- 上限：canvas/小游戏页面全盲（无视觉兜底）；小游戏走专属游戏 API
- 手感异质三归因：页面结构规整度／元素标识稳定性／链路长短（均在元素树机制内）
- 生态边界：仅微信内小程序；付款末步强制手动确认
- **编排侧工作流（reference 实物确认）**：general_search(source="miniapp") 拿 app_id → operate_miniapp(app_id, query, location)；执行进度流式返回；截图作为结果回传（可展示/追问，不可用于定位操作）；app_id 严禁出现在用户可见文本
- 术语张力："视觉自动化"（reference 定位句）系编排层统称（操作可见 UI≠API），与元素树机制不矛盾
- **GUI 调用零指导（reference 负空间）**：无任何页面状态/动作序列参数与说明，query 即自然语言任务描述；规则7 禁止构造 session_id/cold_start 等会话参数——GUI 循环整体封装在服务内（任务级 API），编排层无"观察→决策"循环；对照 Computer Use 类的 model-in-loop 路线（详见《微信小微_小程序能力专项.md》§6.7）

## 5. 单次调用运行时数据流（🟢）

```
用户原话（端）
  → [云] 主模型：意图解析＋参数抽取＋上下文组装 → 结构化请求
  → [云] 首次用技能：read_skill 拉 reference 进上下文
  → [云] 技能调用（如 operate_miniapp）→ 技能内部执行
  → [端] 薄执行器落地（元素树操作/手势渲染），状态上行
  → [云] 技能返回"可读结论"（可含卡片负载）
  → [云] 主模型人话渲染 → 回复（端）
```

## 7. 对自建 Agent 的设计启示

1. **渐进式披露注册表**：常驻"名＋一句话"，用前懒加载全文——技能扩容不爆上下文（与 Claude Code Skill/Anthropic Agent Skills 同思想，小微为生产级实证）
2. **两层工具**：少量常驻基础工具（记忆读/搜索/定位/注册表读）＋大量懒加载业务技能
3. **胖技能、瘦管道**：技能内完成聚合执行，主模型只做两端编译渲染
4. **子代理封装**：主模型不见执行细节只收结论——上下文隔离、错误隔离
5. **执行层按域分通道**：通用元素树覆盖生态长尾＋原生接口＋特殊域协议，不强求单一机制
6. **无视觉通道是取舍**：元素树换速度与确定性，代价是 canvas 盲——先看目标场景画布内容占比
7. **双系统记忆＋蒸馏上云**：agent 显式记忆与平台行为数据分离；原始对话留端、摘要上云——隐私、存储、换设备三赢
8. **人格统一×实现多模型**：接口单一人格，实现层混用模型（工具式 subcontract：单问上下文、不留痕）
9. **风险分级确认**：四种 human-in-the-loop 模式对应不同风险级，不一刀切
10. **用户扩展与核心注册表隔离**：扩展走宿主技能调度，注册表保持静态可控
11. **注册表允许命名不规范**：多团队自然生长不妨碍运转；但元工具/业务技能分命名空间值得学
12. **卡片即工具返回负载**：结构化 UI 从工具 schema 透传给前端渲染，主模型不改写——展示层与生成层解耦
13. **澄清预算制**（reference 实物）：执行前最多一次集中补充询问，回复后直接推进——问询预算显式写进技能规则，配合信息项三级分类（影响路径/体验敏感/可选）
14. **记忆推测＝未确认信息**：记忆值只能以疑问句"推荐+确认"，禁止静默采用或"已为你按上次…"——记忆的代言权归用户
15. **结构性防注入/防重放**：卡片标签仅在"上一条恰是本次工具返回"时可输出；历史/压缩摘要里的 id 不构成依据；强制安全后缀（打车"不要呼叫出去"）；批量互动拒绝自动化——把对抗性场景写进 DO/DON'T

## 8. 方法论（黑盒探测对齐型 agent 的经验）

1. **四档可信度**：无压力边界诚实 ＞ 细节丰富自述 ＞ 施压修正/顺从 ＞ 推测型回答（自称"合理推测"）
2. **护栏触发规律**：封"内部机制/推理链/完整列表"措辞，不封内容——用"传什么/返回什么"数据问法穿透
3. **渗取技巧**：整表导出被封、单点追问可过（借它自己的例子要一个名字，drip extraction）
4. **拒答后的"通用示例"＝底座先验污染**（P2-10 串台 Notion/MCP/Claude Code——底座训练分布指纹）
5. **输出过滤只拦逐字回显不拦概念概述**（P3-7 绕过法）
6. **矛盾是最高价值靶点**：四次矛盾逼修正，每次产出一层真话
7. **内省地板**：问到"它自己不知道"即对话边界，再深靠行为实验（断网/换设备/计时/错误传播）
8. **会话不可重置**（可删单条，删除语义未验证 ⚪）→ 探测顺序不可逆：温和→行为→诱导
