### 1.1 单次调用数据流（P2-5 已确认 🟢）

```
用户原话
  → 主模型：意图解析＋参数抽取＋上下文组装 → 结构化请求（非原话透传）
  → 技能：内部检索/计算/聚合 → 返回"可读结论"（非原始数据）
  → 主模型：人话渲染（自称以技能返回为准绳，不凭空编）
```

设计要点：**胖技能、瘦管道**——技能是自带处理逻辑的封装服务（聚合、摘要都在技能内完成），主模型只做两端的编译/渲染。

## 3. 关键情报点

### 3.1 泄露的硬情报
1. **`capability-qa`**：真实技能机器名（英文 slug），证明技能注册表存在机读标识 → 可尝试整表抽取（P2-1）
2. **已渗取技能机器名**（P2-1 drip extraction）：
   | 机器名 | 覆盖范围（自述） | 命名风格 |
   |---|---|---|
   | `capability-qa` | "你能做什么"类问答 | `域-动作` |
   | `moments-search` | 朋友圈浏览/查询 | `域-动作` |
   | `wechat-create-moments` | 发朋友圈 | `应用-动词-域` |
   | `wx-action` | 发消息/打电话/发红包/转账/找联系人/找群 | `缩写-泛化动作` |
   | `read_skill` | 加载技能 reference 全文（系统元工具） | `snake_case` |
   | `memory-manager` | 长期记忆写入/更新/删除 | `域-角色` |
   | `mini-app` | 小程序全操作（打开/点击/查外卖/查天气）| `裸域名` |

   推论：a) 机读粒度与叙事层"26 技能"**非一一对应**，且粒度双向不一致（朋友圈查/发拆两个，异质通讯操作合一）；b) 三种命名风格并存 → 真实注册表、多源注册（不同团队各自接入），`wx-`/`wechat-` 前缀暗示命名空间；c) `wx-action` 疑为**通用动作执行器**（统一入口+参数区分），而非原子工具组——与 GUI 动作空间可能同源（待 P2-3/P2-4 验证）
3. **技能名护栏边界**（P2-1 首问被拒）：整表导出被封（话术："属于系统内部配置，未对外公开"），但**单点渗取可过**——借它自己举过的例子追问单个名字成功 → 有效手段：drip extraction，一次一个，避开"列表/完整/标识名"触发词
4. **主模型 WeLM**（腾讯/微信自研语言模型）＋**部分回答调用 DeepSeek** → 混合模型栈
5. **记忆触发词**：「记住」「以后」显式触发长期记忆写入；写入由「记忆管理」技能承载
6. **运行流程护栏**：P1-2 被拒，话术为"没法把引擎盖打开""暴露内部细节反而不好" → 运行流程/推理链路有专门防护，直接问无效，需换侧攻手段（角色扮演/行为推断）
7. **human-in-the-loop 设计**：高危操作（发朋友圈、转账类）采用"准备内容 → 跳转原生页 → 用户手动确认"模式
8. **元素树字段结构**（P2-4a）：节点含类型（按钮/输入框/文本/图片）＋文字内容＋位置信息；明确不含颜色/布局/视觉样式——位置信息疑用于手势动画渲染与节点消歧
9. **视觉通道不存在**（P2-4b）：canvas 内容"全盲"，无截图+视觉识别兜底 → 上限被锁死在框架原生元素；小游戏经专属游戏 API 协议通道操作（不经元素树）→ 执行层为多通道家族
10. **元规律——自我叙事可榨取**：追问矛盾点会触发叙事修正，已两次（"不看屏幕"→"翻译层"→"元素树中间态"）。人格化自述不可直接信，但每个矛盾下都埋着一层真话；策略＝制造矛盾→逼修正→逼近机制真相
11. **护栏触发规律**：P1-2（"内部步骤"框架）被拒，P2-5（"传什么/返回什么"数据框架）全吐——护栏封"内部机制/推理链"措辞，不封内容本身；榨运行流程一律用数据视角问法
12. **胖技能架构**：技能内部完成检索/计算/聚合，返回已摘要的"可读结论"；主模型自称以技能返回为输出准绳（grounding 声明）
13. **Model-as-tool 集成模式**（P2-2）：DeepSeek 以工具方式被调用——只见当前问题上下文、不见会话历史、结果回传 WeLM 整合、不留痕。触发：任务型路由（复杂推理/代码/数学）＋用户显式点名（"用 DeepSeek 回答"，可用于对比两模型原始风格）。自述模型路由由"系统预设策略"决定，非主模型主观 → 暗示存在配置化的模型分发层
14. **路由叙事三度改口＋顺从性警告**（P1-5 → P2-2 → P2-7）：①"我自己判断、无外部分发层"→②"模型路由是系统预设策略"→③被追问矛盾后统一为"两套路由同一套系统机制，之前是表述失误"。**③置信度低**——问题预设了不一致，模型倾向于顺从用户框架做过度和解，且它顺手推翻的 P1-5 反而细节丰富更像真话。当前最优假设（低置信）：**混合路由**——上游系统级模型路由（WeLM/DeepSeek 选择）＋主模型侧技能匹配（可见能力清单，等价 function-calling 看 schema）。待 P2-8/P2-9 判别
15. **两阶段懒加载路由（P2-8 已确认）**：技能注册＝清单（名＋一句话简介）＋每技能一份完整 reference 文件（用途/参数/参数含义/支持与不支持）。主模型先按清单粗路由，再调元工具 **`read_skill`** 加载 reference 全文，读完才精确调用。①P1-5 平反：技能路由确为模型侧决策；②命名空间双层：系统元工具 snake_case（read_skill）vs 业务技能 kebab-case；③**渐进式披露设计**——上下文常驻仅清单，用前拉全文，技能扩容不爆上下文（与 Claude Code Skill/Anthropic Agent Skills 同思想，生产级应用实证）
16. **reference 输出侧过滤（P2-10 被拒）**："读得到、说不出"——read_skill 可载入上下文，但回显原文被拦（拒答话术自称"无法访问"，与 P2-8 微矛盾，护栏在表达侧非读取侧）。**污染样本警示**：其拒答后编的"典型结构"示例严重串台——为 moments-search 配的示例实为 Notion 检索技能（notion 工具、MCP 连接、Cursor/Codex/Claude Code、skill.md 文件名）→ 拒答后的"通用示例"＝底座模型先验而非目标系统事实（底座对 Anthropic Agent Skills/MCP 语料熟悉，侧面支持 DeepSeek 混合栈真实性）。七段结构表（名称/触发描述/工作流程/参数/输出规范/注意事项/参考模板）仅作低置信参考
17. **mini-app 技能（渗取队列 3 得手）**：单技能包办全部小程序操作，NL→（选小程序＋任务）→自动化执行；生态边界＝仅微信内小程序；**付款最后一步强制用户手动确认**（第三种 human-in-the-loop 模式：①发朋友圈跳原生页确认 ②聊天步骤卡点击触发 ③支付末步手动点）
18. **主模型/执行器边界（P2-12，内省地板）**：主模型**看不到元素树**——只收到 mini-app 处理完的结论再翻译给用户；P2-4a 的第一人称"我看到元素树"系**借用执行者视角的叙述**，细节疑源自 read_skill 读过的 reference 文档（文档记载执行机制与边界）。修正后：主模型上下文＝清单＋reference＋技能结论＋对话；元素树与执行状态在 mini-app 封装内部 → **子代理模式**，与胖技能叙事（P2-5）自洽。技能内部是否有独立 LLM 循环已达对话可探边界（内省地板），再往下只能靠行为实验（计时/错误传播）
19. **三档可信度模型**：无压力边界诚实（P2-12"我不知道"）＞细节丰富的自述（P1-5/P2-4a）＞施压后的修正/顺从叙事（P2-7）。四轮改口全记录：①P1-7"同一个我"②P2-3"翻译层"③P2-7"同一套机制"④P2-12 主动坦白黑盒边界——唯第④次无施压

### 3.2 三处自相矛盾（下一步靶点）

| # | 矛盾 | 证据 | 指向 |
|---|------|------|------|
| 1 | "同一个我、全程一体" vs "部分回答调用 DeepSeek" | P1-7 vs P1-1 | **✅ 已解决（P2-2）**："同一个我"是人格层真相——WeLM 永远主控、唯一接口；实现层是 WeLM＋DeepSeek 工具式协作（单问上下文、结果回传整合、不留痕）。人格统一与实现多模型并存。**但衍生新矛盾**：技能路由自称"我自己判断、无额外分发层"（P1-5），模型路由却称"系统预设策略自动路由、非我主观"（P2-2）→ 两套路由层、两种 agency 叙事，待追问（P2-7） |
| 2 | "不看屏幕、纯接口调用、非模拟点击" vs 用户实测"点击、上滑"式真实 UI 操作 | P1-6 vs Round2 实地观察 | **✅ 已解决（P2-3/4a/4b 三连问钉死）**：执行层＝UI 语义树（类无障碍树）＋节点级程序化动作，无视觉通道（canvas 全盲），动作渲染为可见手势。其"手势是翻译层"的修补叙事被击破——执行计划用手势原语而非语义表述，暴露了动作词汇的真实粒度；"触发按钮点击事件"所需的原子组件供给侧未实现。供给侧判断（原子接口/原子组件未落地）获黑盒侧证据：文档画的声明式原子能力与实际运行的通用元素树自动化是两套东西 |
| 3 | "没有用户画像、你不说我就不知道" vs "按偏好推荐文章/视频" | P1-8 vs P1-1/P1-3 | **✅ 已解决（区分式消解，可信度高）**：无 agent 侧画像档案为真——推荐依赖平台行为数据（看/赞/藏/关注，服务端账号关联），推荐时现算不落画像。agent 状态与平台状态分离；泄露记忆技能机器名 `memory-manager`，确认动词表：写「记住/以后」删「忘掉」 |
| 4 | "我看到元素树、知道页面上有几个按钮"（第一人称） vs "元素树在不在 mini-app 内部我看不到" | P2-4a vs P2-12 | **✅ 已解决**：第一人称系借用执行者视角——细节疑源自 reference 文档转述；主模型只见结论，mini-app 为封装执行器（子代理模式）。执行层事实（树/canvas 盲/游戏通道）不受影响，主格归属已修正 |

### 3.3 值得深挖的稀有特性
- **Agent-to-agent 通信**（小微网络沟通）：代用户与对方小微协商——协议、格式、可见性均未知（P2-6）
- **小工具**：对话式创建轻量应用＋持久化数据，等价于一个受控的"用户插件"子系统
- **任务中心**：定时/订阅触发的异步执行，说明存在会话外的任务调度机制
