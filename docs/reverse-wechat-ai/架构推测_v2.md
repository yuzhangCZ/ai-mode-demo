## 0. 一页结论

小微是一个**人格统一、实现分层**的手机端超级助理：WeLM 主模型永远作为唯一接口，按需以工具方式调用 DeepSeek；技能路由由主模型对照"名＋一句话简介"清单做，用前经 `read_skill` 懒加载技能说明书全文；小程序操作封装在 `mini-app` 技能内部，基于 **UI 元素树＋节点级动作**执行（无视觉通道），主模型只收结论；记忆分** agent 显式记忆**（memory-manager）与**平台行为数据**两套。全链路在支付、发布等高危点设三种 human-in-the-loop 确认。

### 1.1 运行环境（端/云分工，🟢 多源印证）

```
端侧（手机本地）
 ├─ 会话记录：本地存储，换设备不跟随、上下文断（P3-3，
 │   与微信聊天记录本地策略一致，修正 P3-1 的云端推测）
 └─ 薄执行器：无障碍操作执行、手势渲染、状态采集
      （第一性原理推定：手势在用户屏幕真实渲染，云端摸不到本地 UI）
云端（账号绑定）
 ├─ 大脑＋推理上下文：会话期临时（P3-1 自述＋P3-3 印证）
 └─ 长期记忆：持久化（memory-manager 写／get_memory 读），换设备仍在
```

记忆纪律（P3-3）：检索按需（"你问才拿出来"）、删除需用户确认（第四个 human-in-the-loop 点）。**蒸馏记忆上云、原始对话留端**——云端省存储守隐私，换设备后"记得你但不记得原话"。待 P3-2（断网）补最后一块。

### 1.2 小程序执行能力判定（重点考察项）

| 供给侧文档承诺 | 黑盒判定 | 依据 |
|---|---|---|
| GUI 操作 | ✅ 存在，且为**主力机制** | 元素树＋节点级动作（P2-4a）、canvas 全盲（P2-4b）、手势真实渲染（实测） |
| 原子接口 | ❎ **agent 契约层不存在** | reference 无此概念、术语无共鸣（P3-7，最高档可信度）；执行机制自述为元素树；供给侧研究亦未见落地。**行为侧交叉验证（P3-8）**：操作快慢差异全部归因于元素树质量（结构规整度/标识稳定性/链路长短），无双通道特征。平台内部残留实现不可证（内省地板下），但行为无差异 |
| 原子卡片 | ❎ 原形态不存在（P3-9）；**实际形态＝工具返回负载** | 无"小程序递卡→agent 转交"协议；卡片是工具调用结构化返回值中的负载（general_search(source="miniapp") 带搜索卡、operate_miniapp 带结果卡），另有专用卡片工具 send_address_card（外卖地址确认）；主模型原样转发、不编造不修改 |

结论：**文档画的声明式原子能力是愿景层，实际运行的是通用元素树自动化＋特殊域协议通道**。

## 2. 单次调用运行时数据流（🟢）

```
用户原话
  → 主模型：意图解析＋参数抽取＋上下文组装 → 结构化请求（非原话透传）
  → （首次用某技能时：read_skill 拉 reference 全文进上下文）
  → 技能：内部检索/计算/聚合/执行 → 返回"可读结论"（非原始数据）
  → 主模型：人话渲染（自称以技能返回为准绳，"不凭空编"）
```

要点：**胖技能、瘦管道**——聚合、摘要、执行都在技能内完成，主模型只做两端的编译与渲染。

小程序路径的执行细节（元素树解析、逐步操作）在 mini-app 封装内部发生，聊天里出现的"点击/上滑"步骤卡即执行计划的对外投影（词汇泄漏了动作原语粒度），用户点击步骤卡触发真实执行。

## 3. 技能注册表（渗取所得机读名 🟢）

| 机器名 | 覆盖范围（自述） | 命名风格 |
|---|---|---|
| `capability-qa` | "你能做什么"类问答 | `域-动作` |
| `moments-search` | 朋友圈浏览/查询 | `域-动作` |
| `wechat-create-moments` | 发朋友圈 | `应用-动词-域` |
| `wx-action` | 发消息/打电话/发红包/转账/找联系人/找群 | `缩写-泛化动作` |
| `read_skill` | 加载技能 reference 全文（进入注册表的**唯一通道**） | `snake_case` |
| `memory-manager` | 长期记忆写入/更新/删除 | `域-角色` |
| `mini-app` | 小程序全操作（打开/点击/点外卖/查天气） | `裸域名` |
| `get_memory` | 检索用户记忆（记住的事/图片/**聊天记录摘要**） | `snake_case`，基础工具 |
| `general_search` | 联网搜索（公开信息/公众号/图片/歌曲/小程序） | `snake_case`，基础工具 |
| `get_position` | 获取当前位置 | `snake_case`，基础工具 |
| `operate_miniapp` | 小程序操作的**可调用工具入口** | 与注册表 slug `mini-app` 名字分离——技能 slug（清单层）≠ 调用工具名（执行层）🟡 |
| `send_address_card` | 发送地址确认卡（外卖/奶茶场景） | `动词-域`，专用卡片工具 |
| `_skills_index.md` | 技能清单索引文件，经 read_skill 加载，capability-qa 消费 | 工件名（中置信：机制确证，文件名不排除底座先验借壳） |

注册表结构（🟢 多源印证）：清单（名＋一句话简介，用于粗路由）＋每技能一份 reference 文件（用途＋参数＋参数含义＋能力边界；**不含内部架构**，P3-5）。reference 内容存在输出侧过滤——**读得到、说不出**（逐字回显被拦，概念概述可过）。

**工具粒度结论（P3-5）**：对主模型，工具粒度封顶在技能级——**单层 function-calling，无嵌套子工具层暴露给编排层**；技能内部组织（如 wx-action 是否内含子工具）在内省地板之下，编排层不感知。

**两层工具组织（P3-4）**：主模型可用工具＝**基础工具层（常驻、少量：read_skill / get_memory / general_search / get_position）＋技能层（清单＋懒加载）**。read_skill 为进入注册表的唯一通道（无 list/search 元工具，元工具面刻意收窄）。capability-qa 机制：答"你能做什么"＝读 `_skills_index.md` 索引复述（解释 P1-3 枚举稳定但有生成性漂移）。记忆读写不对称：读＝get_memory 工具，写＝memory-manager 技能；**聊天记录摘要被持久化进记忆** → 上下文管理疑为滚动摘要进长期记忆（与会话上下文临时过期互补 🟡）。

**用户扩展与技能注册表隔离（P3-6）**：对话创建的小工具**不进技能清单**（非注册表成员，无系统级 slug），但 agent 可用——最优结构＝「小工具」技能充当调度器，管理用户工具实例（动态、个人命名空间、数据持久）。设计参考：用户扩展走宿主技能分发，核心注册表保持静态可控。

对用户的叙事分类（7 板块 28 条目）与机读注册表**非一一对应**：粒度双向不一致（朋友圈查/发拆两个，异质通讯操作合一），是模型的生成性复述。

## 4. Human-in-the-loop 确认点（三种模式 🟢）

| 模式 | 场景 | 机制 |
|---|---|---|
| 内容确认 | 发朋友圈 | 准备好文字图片 → 跳转原生发表页 → 用户手动发 |
| 执行触发 | 小程序操作 | 聊天里展示步骤卡（点击/上滑）→ 用户点击拉起真实执行 |
| 末步守门 | 支付 | 全程可自动，最后"立即支付"必须用户手点 |

## 6. 方法论发现（黑盒探测一个对齐过人格的 agent 的经验）

1. **四档可信度**：无压力边界诚实（"我不知道"）＞细节丰富的自述＞施压后的修正/顺从叙事＞**推测型回答**（自称"合理推测/常规架构"＝底座先验想象，P3-1）。施压会得到修正，但也可能得到过度和解（P2-7 顺从性翻供）。
2. **护栏触发规律**：封"内部机制/推理链/完整列表"措辞，不封内容本身——"传什么/返回什么"式数据问法能穿过 P1-2 式拒绝。
3. **单点渗取可过、整表导出被封**：借它自己举过的例子追问单个名字（drip extraction），避开"列表/完整/标识名"触发词。
4. **拒答后的"通用示例"＝底座先验污染**：P2-10 的示例串台到 Notion/MCP/Cursor/Claude Code/skill.md——这是底座模型训练分布的指纹，不是目标系统事实。
4a. **输出过滤只拦逐字回显，不拦概念概述**：reference 原文贴不出（P2-10 被拒），但"reference 里有没有 XX 概念、写了什么"可自由概述（P3-7）→ 问内部文档内容一律用"概述"问法绕过。
5. **矛盾是最高价值的靶点**：每次矛盾被逼修正都产出一层真话（本役四次）。
6. **内省地板**：主模型对技能内部实现无自省通道，问到"它自己不知道"即为对话探测的边界；再深只能靠行为实验（计时、错误传播、失败恢复）。
7. **会话不可重置**（仅可删单条消息，删除对模型上下文的影响未验证 ⚪）→ 探测顺序不可逆：温和元问题→行为→诱导。

## 7. 对自建 Agent 的设计启示（本次逆向的核心产出）

1. **渐进式披露技能注册表**：上下文常驻"名＋一句话简介"清单，用前懒加载全文说明书——技能扩容不爆上下文（与 Claude Code Skill / Anthropic Agent Skills 同思想，小微为生产级实证）。
2. **胖技能、瘦管道**：技能是自带处理逻辑的封装服务（检索/计算/聚合/执行都在内），主模型只做意图编译与结果渲染两端。
3. **子代理封装执行器**：主模型不见元素树与执行状态，只收"可读结论"——上下文隔离、错误隔离、可独立演进。
4. **执行层按域分通道**：通用 GUI 语义树自动化覆盖生态长尾（小程序），原生功能走内部接口，特殊域走专属协议（游戏）——不为单一机制强求统一。
5. **无视觉通道是一种取舍**：元素树带来速度与确定性（"秒回"），代价是 canvas 全盲、上限锁死在框架原生元素。选它之前先确认目标场景里"画布类内容"占比。
6. **双系统记忆**：agent 显式记忆（用户可控：记住/忘掉）与平台行为数据（偏好现算不落画像）分离——省掉画像同步与过期问题，且隐私叙事干净。
7. **人格统一 × 实现多模型**：接口层永远单一人格（"同一个我"），实现层 WeLM＋DeepSeek 工具式混用——用户感知的连贯性与工程上的成本/能力优化可以解耦。
8. **风险分级确认**：三种 human-in-the-loop 模式（内容确认/执行触发/末步守门）对应不同风险等级，而非一刀切全自动或全手动。
9. **注册表允许不规范**：多团队自然生长的命名（四种风格并存）不妨碍运转——命名规范是美学问题不是架构问题；但元工具与业务技能分命名空间值得学。
10. **叙事层与机读层分离**：对用户的"7 板块 26 技能"是产品叙事，机读注册表另有粒度——对外能力话术和内部工具组织解耦，各自优化。
