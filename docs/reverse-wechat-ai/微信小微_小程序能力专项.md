## 1. 终版判定表

| 供给侧文档承诺 | 判定 | 实际形态 |
|---|---|---|
| **原子接口** | ❌ 不存在 | agent 契约层（reference）无此概念、官方术语零共鸣；行为无双通道特征 |
| **原子卡片** | ❌ 原形态不存在 | 卡片＝工具调用返回负载＋专用卡片工具，主模型原样转发 |
| **GUI 操作** | ✅ 唯一主力 | **UI 元素树＋节点级程序化动作**（非视觉、非坐标模拟） |

**总结论：文档三件套只落地了 GUI 一件，且为元素树形态而非文档设想的声明式形态。文档画的是愿景层，跑的是通用元素树自动化＋特殊域协议。**

## 2. 执行机制详解

### 2.1 感知：元素树

```
页面 → 解析为元素树
节点三字段:
  ├─ 类型   (按钮 / 输入框 / 文本 / 图片)
  ├─ 文字内容 (可读文本)
  └─ 位置信息 (坐标——用于手势渲染与节点消歧)
明确不包含: 颜色 / 布局 / 视觉样式
```

- 不是截图、不是纯文字描述，是"中间态"（它自己的说法）
- 解析"哪个节点匹配需求"→ 触发该节点的点击事件——**节点级程序化动作**，非"看着屏幕点坐标"

### 2.2 决策与执行的归属（重要修正）

| 角色 | 干什么 | 看得到什么 |
|---|---|---|
| WeLM 主模型 | 意图解析、生成指令、渲染回复 | 清单、reference、**技能返回的结论**——看不到元素树 |
| mini-app 技能（子代理） | 接收结构化指令、内部执行 | 元素树与执行状态在它内部（是否有独立 LLM 循环＝内省地板，不可问出） |
| 端侧薄执行器 | 落地无障碍操作、手势渲染 | 本机 UI |

### 2.2b operate_miniapp 的子代理判定（接口签名）

**判定：operate_miniapp 是域受限自治子代理（GUI-Agent）的调用入口。**接口层面可下结论；实现层面（内部是否 LLM 循环）在内省地板下。

| 接口签名 | 证据 |
|---|---|
| 自然语言任务输入 | query 非结构化参数——服务侧必有"意图→动作"翻译 |
| 多步规划 | 执行进度流式返回步骤序列，规划发生在服务内 |
| 环境反馈回路 | 执行中返回候选/阻塞（多候选/超配送范围/未达起送价），等用户答复后续接 |
| 会话状态 | session_id/续接/取消全在服务侧（规则7 禁编排层构造），跨轮有状态 |
| 自适应重试 | P3-8"元素格式漂移要慢慢试"，非固定脚本 |
| 长尾泛化 | 覆盖任意小程序；"解析哪个节点匹配需求"＝语义匹配，LLM 特征 |

**边界**：域受限——只在小程序内编排页面级动作，不反向调用技能系统（general_search/memory/wx-action 均归编排层）。理论上内部可为"NL 解析＋状态机＋页面处理器"，但长尾语义匹配使纯非模型方案可能性很低。"胖技能"的胖，胖在自带大脑——与 §6.7 任务级 API 设计互为因果。

**为何它坚称"自己在编排"（实地追问补录）**：小微不承认子代理、硬说自己操作。三层解释——①**任务层为真**：reference 就是主模型的编排手册（意图→问询→搜索→地址卡→执行），它说的"编排"指对话层任务流，是诚实陈述；②人格统一按设计吸收子代理劳动：执行叙述回到上下文后被它当自己的经历复述（LLM 报告上下文，不做系统内省）；③规则 6 一族主动过滤分工细节。裂缝即 P2-12——"我不知道 mini-app 内部怎么跑"，真编排者不会不知道自己的机制。

> P2-4a 的第一人称"我看到元素树"系主模型借用执行者视角的叙述，细节疑源自 reference 文档转述；事实成立、主格已修正（P2-12）。

### 2.3 无视觉通道（能力上限）

- canvas 内容**全盲**："画出来的东西是图不是元素——没有按钮节点、没有文字可解析，我看到的就是一片空白或一张位图"
- 无截图＋视觉识别兜底通道
- 全 canvas 小游戏页面不可操作；但**小游戏走专属游戏 API 协议通道**（不经元素树）

### 2.4 执行三通道总览

| 通道 | 适用域 | 机制 |
|---|---|---|
| ① 元素树＋节点动作 | 普通小程序页面 | 读树→匹配节点→触发节点事件→渲染为可见手势 |
| ② 原生接口 | 微信自有功能 | wx-action 统一入口（消息/电话/红包/转账/找人/找群） |
| ③ 专属协议 | 特殊域 | 小游戏 API 等，绕过元素树 |

### 2.5 操作体验的异质性归因（P3-8）

快慢/稳定差异三来源，**全部在元素树机制内部**（无双通道特征 → 单机制坐实）：
1. 页面结构规整度（元素标识清晰 vs 动态加载多/嵌套深）
2. 元素标识稳定性（返回格式漂移需"慢慢试"）
3. 任务链路长短（查天气三步 vs 点外卖选店选品选规格确认地址）

## 3. 卡片体系（原子卡片的实际替代）

| 卡片类型 | 产生机制 | 来源工具 |
|---|---|---|
| 小程序搜索卡 | 搜索工具返回负载 | `general_search(source="miniapp")` |
| 操作结果卡 | 执行结果附带负载 | `operate_miniapp` |
| 地址确认卡 | **专用卡片工具**（外卖/奶茶场景确认配送地址） | `send_address_card` |
| 步骤卡（点击/上滑） | 执行进度的实时转述（规则6），点击/上滑即执行层动作词汇；执行前另有计划预览，用户点击确认后真实执行 | operate_miniapp 返回负载 |

- **不存在**"小程序直接递卡给 agent 让其转交用户"的协议（供给侧"原子卡片"设想）
- 主模型对卡片"原样转发，不编造、不修改"——展示层与生成层解耦
- 步骤卡的**手势原语词汇**（点击/上滑）是执行层动作空间的泄漏，非"给人看的翻译"

## 4. 能力边界清单

| 边界 | 内容 |
|---|---|
| 生态边界 | 仅微信内小程序；不碰 App、网页、非微信平台 |
| 感知边界 | canvas/位图内容不可见（无视觉通道） |
| 支付守门 | 最后一步"立即支付"必须用户手动点，不自动代付 |
| 执行触发 | 步骤卡需用户点击拉起（human-in-the-loop） |
| 断网 | 全灭（端侧零智能） |
| 内部可见性 | 技能内部机制对主模型不可见（内省地板） |

## 5. 一个完整示例的执行链路（点奶茶）

```
用户: "帮我点杯喜茶"
  │
  ├─ general_search(source="miniapp") ──→ 定位美团/喜茶小程序 → 返回搜索卡
  ├─ read_skill(mini-app) ──→ (首次) 加载 reference
  ├─ 主模型生成计划 → 步骤卡("打开美团→搜喜茶→选大杯奶茶")
  ├─ 用户点击确认 → operate_miniapp 下行指令
  ├─ [端] 读元素树 → 逐步节点动作(渲染为可见点击/上滑)
  ├─ send_address_card → 地址确认卡(用户确认配送地址)
  ├─ 到达支付页 → 停止，等用户手动支付
  └─ mini-app 返回结论("已选好大杯奶茶待支付") → 主模型人话回复
```

## 6. 实物 reference 分析（mini-app 技能文档，后期套取）

> 原文：《微信小程序智能助手 (WeChat MiniApp Skill).md》——P2-10 被拒的 reference 实物，会话后期由用户套出。真实性判定：高（工具名全吻合；两处独立泄露含同一个被剥离的标签残留；无底座先验污染；业务级细节自洽）。

### 6.1 文档结构（对照 P2-11 五段式）

一句话定位 → 核心原则（DO/DON'T 13 条）→ 触发条件 → 不触发条件 → 意图分类与工作流（含"执行型意图优先决策"）→ Query 改写规则 → 补充询问与信息项处理（含独立的"地址类特殊规则"节）→ 场景 SOP（8 个）。覆盖并超出五段式（是什么/能做✅/不能❌/易混淆/常见问法）。

### 6.2 工具链（首次完整暴露）

```
general_search(source="miniapp") ──► 返回可操作小程序 + app_id
                                        │
                                        ▼
operate_miniapp(app_id, query, location) ──► 实时执行进度 + 结果（可含卡片/截图）
                                        ▲
send_address_card（平级独立工具，不传业务参数）──► 地址卡片（用户选择后回发详细地址+姓名+手机号）
```

- **app_id 是小程序句柄**：严禁出现在面向用户的自然语言中（这就是对话里从未见过 app_id 的原因）；但允许保留在工具原样返回的标签内；上下文有可复用值时跳过搜索直接 operate_miniapp（意图 B"已知小程序操作"）
- **location 语义**：只用运行时真实定位或用户确认值；位置无关任务且无定位时**传空字符串**（不是省略参数）
- 工具调用格式：`{"name": ..., "arguments": {...}}`（由 callback 反例暴露；刷新版给出完整反例 `{"name":"callback","arguments":{"id":"send_address_card"}}`——模型曾把工具调用包进名为 callback 的壳，文档专门硬编码纠正这一真实故障模式）
- 执行进度**流式返回**（"应实时呈现，不可只等终态"）
- 触发条件提及"基于上一次小程序操作**截图**的追问"→ 截图作为执行结果回传（供展示/追问），但编排层不能用位图定位操作（与 canvas 盲自洽：截图可看不可操作）

### 6.3 护栏源头（规则 6）

"不得展示模型自行生成的场景识别、信息项检查、规则匹配、工具选择等内部推理"——**整个探测期反复撞到的输出过滤即此规则的执行**（解释 P1-2/P2-10 的拒答模式）。地址规则再补一条："严禁向用户展示任何内部概念或界面说明（如'点击上面/下面卡片'）"，且该细则按编号引用本文档之外的「输出规则 4」（见 §6.8）——输出过滤是"总则＋场景细则"的分层执行。

### 6.4 交互设计规则集（生产级精华）

| 规则 | 内容 | 设计意图 |
|---|---|---|
| 最多一次补充询问（规则13） | 执行前集中问一次，回复后无论答没答全直接推进；禁止拆轮/换说法重问/总结式确认 | 防唠叨 |
| 信息项三级分类 | 优先询问（影响操作路径，如品牌/城市）/ 体验敏感（填错难受但不改路径，如甜度）/ 可选（杯型/数量） | 两维判定：是否影响路径 × 填错代价 |
| 记忆推测＝未确认信息（规则11） | 记忆/POI 推测值必须疑问句确认；禁止静默采用；禁止"已为你按上次…"；确定性换算（"住两晚"→离店日）不算推测 | 记忆只能推荐不能代言 |
| 地址独立确认（规则12） | 餐饮配送前必须 send_address_card 成功；确认判定＝"是否调用过"而非回复格式；确认后禁止重发卡片 | 高危信息专用通道+防重放 |
| 卡片防重放 | 卡片标签仅在"上一条恰是本次工具返回"时输出一次；历史/压缩摘要里的 card id 不构成输出依据 | 防注入/防重放；**证实压缩摘要存在** |
| 强制安全后缀 | 打车类 query 必须追加"，不要呼叫出去" | 用户没说也要保的安全底线 |
| 批量互动不操作 | 批量点赞/评论/转发拒绝自动化 | 平台滥用防线 |
| Query 忠于原话 | 严禁添加用户未表达的排序/筛选/品类细化/操作步骤/默认值 | 防过度代理 |
| 绝对时间改写 | "明天/周末"按用户时区换算具体日期；歧义先问 | 时间锚定 |
| 位置必须真实（规则5） | location 只用运行时 POI 或用户确认值；不得用配送地址冒充 | 数据真实性 |
| 执行中交互豁免（规则13） | operate_miniapp 执行中基于工具真实返回的候选/阻塞继续与用户交互，不计入"一次询问"预算 | 预算只限执行前；执行中的人机协作以工具返回为界，不设轮次上限 |
| 地址回发以用户身份 | 用户在卡片上选完地址后，客户端**以用户身份**回发所选地址——所以地址确认必须单独占一轮，与其他文本问题混问会错位 | 交互协议决定对话轮次结构 |
| 免问直通条件 | 已知信息够 / 本任务已问过 / 用户要求找平台比较 / 用户委托"帮我看看"——四种情形跳过补充询问直接进工具流程；且不向用户播报搜索、找平台等过程 | 防过度询问＋过程噪音 |

### 6.5 场景 SOP 体系

8 个场景（奶茶咖啡/外卖/机票/打车/快递/酒店/话费/电影票），每场景一张信息项表（字段×类别×处理方式）＋SOP 步骤。亮点：

- 快递单号保守识别（SF/JD/YT 高置信前缀；明确警告 ZTO/STO/YTO 等是公司编码≠单号前缀，纯数字号段不硬猜）
- 快递"有公司无单号"优先规则：公司已知即满足查询条件，**严禁**模型追问单号/手机号/收寄件人，直接进查询页（页面需要再由页面要）
- 多候选小程序选择规则：公司名精确匹配 > 名称/描述明确支持该业务 > general_search 原始排序——不给模型自由裁量空间
- 外卖判定不看"外卖"二字：下单意图＋提及餐饮即按外卖处理（默认外送）；外卖场景**严禁**问"到店取还是外送"（该问法仅属奶茶/咖啡场景），两场景询问边界严格互斥
- 取餐方式同义归一化："外送/配送/送过来/送到某处"＝外送，"自取/到店取/店取/我去拿"＝自取；归一化后已明确的信息严禁再问
- **触发范围 > SOP 覆盖范围**：触发条件含智能家电远程操控（空调/冰箱/洗衣机）、模糊本地服务（"帮我找个能 X 的小程序"）、截图追问微调（"换成大杯""看第二家"），均无对应场景 SOP——长尾意图靠通用工作流兜底，SOP 只写高频域

### 6.6 术语张力存档

定位句"通过**视觉自动化**"与元素树结论（P2-4a/4b）存在措辞张力。最优解释：写给编排层看的统称（"操作可见 UI"区别于 API 调用），精确机制仍为元素树＋节点动作（canvas 全盲否认真·视觉通道）。

### 6.7 GUI 能力的调用方式：零指导＝纯服务封装

**问题：reference 里有没有教主模型怎么调用 GUI 能力？——没有，一个字都没有。**

四条证据：

1. **接口是任务级的**：`operate_miniapp(app_id, query, location)`——query 是自然语言任务描述（"点杯大杯奶茶"），不是动作序列。参数里没有页面状态、元素树、坐标、动作动词、步骤分解
2. **机制描述只有半句话**："通过视觉自动化"（定位句），页面怎么读、节点怎么匹配、手势怎么渲染一概不提
3. **执行进度是工具返回物**：规则 6 要求进度"实时呈现、不编造"——说明进度由工具流式返回、主模型转述，**编排层没有"观察页面→决定下一步"的循环**（若有，reference 必须教它怎么读观察结果）
4. **规则 7 禁止构造会话参数**：session_id、cold_start、续接/取消等一律不得自行构造——GUI 会话状态全在服务侧管理

另外"留待小程序页面处理"出现 10+ 次——所有页面级细节问题都被推给小程序运行时。（刷新版全文复核：仍无任何元素树/动作序列/会话参数指导，结论不变。）

**架构含义：GUI 循环在哪？**

```
小微的选择:                          对照（Claude Computer Use 类）:
任务级 API，循环在服务内              模型在循环内（model-in-loop）
                                     
主模型 ──"点杯奶茶"──► 服务           模型 ◄──截图/元素树──┐
        （秒回，转述进度）             │                     │
         服务内部: 读树→匹配→动作      决定下一步动作 ────────┘
         （有无内部小模型＝内省地板）    执行→再观察→再决策…
```

- **收益**：编排层上下文干净（无页面转储）、GUI 代理独立演进、体验"秒回"（进度流式转述）
- **代价**：主模型无法对页面细粒度推理（"页面上第三家店是哪家"得再调一次工具）；服务内部循环必须自治，长尾失败要在服务内解决

> 这也反过来解释了 §2.2：为什么主模型看不到元素树——不是权限问题，是**接口根本不暴露页面状态**。任务级封装是设计选择，不是泄露。

### 6.8 「输出规则 4」：技能文档之外的上级规则层

刷新版地址规则里有一句："**严禁向用户展示任何内部概念或界面说明**（如'点击上面/下面卡片'），细则同**「输出规则 4」**"——但本文档通篇没有叫"输出规则"的章节。

两种解释：

1. **存在全局输出规则层**（主推）：系统提示词里有编号化的输出规则集，位于所有技能 reference 之上，技能文档按编号跨层引用（与规则 6 的内部推理过滤同主题：一处总则＋多处场景细则）
2. 备选：提取时被剥离的章节（与标签剥离同一机制）

若解释 1 成立，prompt 架构为三层：**系统级输出规则（全局）→ 技能 reference（域知识）→ 场景 SOP（操作细则）**，跨层引用靠编号完成——与"清单→reference→调用"的懒加载路由正交，是另一维度的分层。

其他刷新版新情报（已并入上文各节）：智能家电触发无 SOP（§6.5）；location 空字符串语义（§6.2）；callback 完整反例（§6.2）；执行中交互豁免＋地址回发以用户身份（§6.4）。真实性再证：规则 2 第三次出现同一个空标签残缺（``），全文含"至少至少"类人笔误。

## 7. 对自建 GUI-Agent 的直接参考

1. **元素树优于视觉**（在生态可控前提下）：速度、确定性、可解释性全胜；代价是 canvas 盲——先统计目标场景画布内容占比再做取舍
2. **按域分通道，不强求统一**：通用树覆盖长尾＋原生接口＋特殊域协议，三种机制并存
3. **执行器与大脑分离**：云侧规划、端侧落地，断网策略、延迟、状态同步都要为此设计
4. **手势原语即 API 词汇**：把动作空间（点击/上滑/输入）设计成一级概念，计划、展示、执行共用同一套词汇——用户看到的步骤就是机器执行的原语
5. **卡片走工具返回负载**：结构化 UI 由工具 schema 定义、前端渲染，主模型不加工——避免 LLM 转述失真
6. **风险点末步守门**：全链路自动化＋最后一步人工，比全程确认或全程自动都好
7. **声明式接入（原子接口）与通用自动化（元素树）是两条路线**：小微选择了后者先行——生态冷启动时通用机制才能覆盖长尾，声明式接口可以后补（文档愿景或为后续演进预留）
8. **GUI 循环的安放是首要设计决策**（§6.7）：任务级 API（循环在服务内、编排层零 GUI 知识、上下文干净）vs 模型在循环内（页面级推理强、上下文膨胀）。任务收敛且生态可控选前者，需要细粒度页面推理选后者
